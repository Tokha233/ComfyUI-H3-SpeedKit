## 最终结果与部署建议

**本轮继续保留 Larry v4 8 步。** 两条 PDMD INT8 路径已完成全部 15 个片段，原 BF16 PDMD 和 8-NFE 外推各完成两个代表片段。PDMD4 确实将代表片段的采样耗时约减半，但与 BF1650 的音视频接近程度未达到当前方案，不能作为无损升级。

## 测量与判定口径

- 业务集是 **5 个故事 × 3 个片段，共 15 个独立片段**；每段约 9–12 秒，768×1344、24 fps，固定原 condition 与 seed。没有把这些片段表述成 15 个 30 秒请求。
- 质量参考为既有 **BF16 50 步完整生成的 MP4**；也直接对比实际冻结 r85 部署输出。没有重新跑 15 次 BF16 50 步；本轮重算所有参考指标。
- 两个代表片段另外重新执行 Larry8，得到与历史 r85 完全相同的视频/音频 latent。共用本轮通用 INT8 VAE 与 FP32 音频 VAE，隔离模型变化。
- 当前通用 VAE 与历史融合 decoder 的导出有小差异：两个代表片段 MP4 SSIM 约 0.9899、LPIPS 约 0.0071/0.0078；PCM 相同。所以“当前真实部署”和“本轮相同 decoder 的 Larry”分别列示。
- 原分辨率逐帧 YUV SSIM/PSNR；LPIPS SqueezeNet v0.1 在 384×672、2 fps 上测量。
- 8 kHz 单声道短窗 log-FFT cosine 与 32 kHz 双声道 STFT cosine 分开。全频 STFT 使用 n_fft=1024、hop=256，t0 对齐，不搜索最佳时移。这里解码的是 AAC 文件；另有直接 latent 和未编码 FP32 PCM 对照。
- SSIM/LPIPS/频谱相似度衡量与参考的接近程度，不等同于主观画质、音色、语义/口型正确率。没有用相似度推导 MOS。
- 两个代表片段的 sampler 采用每方案一次预热、一次正式请求；其余片段用于业务质量覆盖。sampler 时间不含 condition、VAE、视频编码与网络，不等于线上 QPS。

## PDMD 权重与正确接入

原始模型：[pdmd2026/pdmd_4NFE_lora](https://huggingface.co/pdmd2026/pdmd_4NFE_lora)；论文：[PDMD](https://arxiv.org/abs/2609.35768)。PDMD 改变蒸馏训练中的梯度方向，不要求推理时运行 critic。

ComfyUI 转换：[Iwannapose/minimax_h3_pdmd_4nfe_comfyui](https://huggingface.co/Iwannapose/minimax_h3_pdmd_4nfe_comfyui)，固定 revision `ae6ab62d28754b9ce052798b92d9567161568f28`，文件 `minimax_h3_pdmd_4nfe_comfyui_v6.safetensors`，SHA256 `d1d7c9f08782492ebcaa57f9f823899541ee04c48a298692a229683c4b3dd8a1`。

选择 v6 的原因：之前转换存在键名匹配或 SwiGLU gate/value 次序错误。此次 624 个 tensor、208 个目标层全部匹配；q/k/v 合并后 rank=384、alpha=384，其他层 rank=128、alpha=128，完整保留每个原始 LoRA 分支。没有叠在已挂 Larry 的权重上。

配置：strength=1、CFG=1、video/audio shift=12/3。显式创建 5 个 sigma 端点，确认 **4 次实际 DiT 前向**：

```python
u = torch.linspace(1, 0, 5, dtype=torch.float32)
sigmas = 12 * u / (1 + 11 * u)
# [1, 0.972972989, 0.923076928, 0.800000012, 0]
```

原始 scheduler 的 `num_inference_steps` 计入末尾零；不能把 4 个端点误记成 4 NFE。音频由 H3 的双模态 sigma 映射处理。每次采样同时验证 fused norm=400、QKV=200、gate=400 次，所有输出有限。

四条实验路径：

| 标识 | 路径 | 用途 |
|---|---|---|
| PDMD4 / 二次 INT8 | 未挂 Larry 的 INT8 底模 → 反量化 → 合并 PDMD → 再量化 | 评估直接在已有量化底模上接 LoRA 的结果 |
| PDMD4 / 原 BF16 | 原 BF16 底模 → FP32 B@A、按原 dtype 写回 delta 并加到权重 | 检查量化是否为质量下降的唯一原因；DiT BF16、PyTorch attention |
| PDMD4 / 一次 INT8 | 上述 BF16 合并结果 → 一次确定性 ConvRot256 rowwise INT8 | 更合理的 INT8 部署候选 |
| PDMD8 | 第一条同一份 4-NFE 权重执行 8 NFE | 加步外推；不是训练好的 8-NFE PDMD 模型 |

一次量化没有调用随机舍入，按原 INT8 模型 schema 保留未量化层的 dtype。合并和量化流式写入 safetensors，验证 shape、字节长度、全部 tensor 覆盖与最终 SHA；不发布基础模型、业务条件或合并权重。

权重标识：

- BF16 合并：`f6f03228b255856cd79029107fce13badde3cb0fa45edd368165f2ac64f9c012`
- 一次 INT8：`ee238ef9cfa98f93fa3633ad23582835efa85de0d363266d487aa580b85cd0dc`
- 二次 INT8：`915d430b84d565c9a862a92adcb1b1acfba6f66121b526548ec7562f85d3cba8`

INT8 与原 BF16 的差异包含权重量化、非量化层 schema dtype、INT8 attention 与 BF16 attention。不能把这一组生成输出差异称为纯 weight 量化误差。

## Gate 分带调度：未得到稳定增益

比较 old、最新调度 band=0/8/16/32/64 共 6 个候选，10 组实际 gate shape：M=1024/14850/32700/87142/90461，N=5376，K=7168/14336。BF16 输出全部逐值一致。主要业务尺寸没有稳定的实质收益，通常在 ±0.1% 附近。

Ntile=21，band32/64 大多已经覆盖全部 N；普通大 N GEMM 的收益不能搬到这个 gate 上。没有为负结果另发性能 PR。原始记录见 [gate-bench](../evidence/pdmd-kitchen-1001/remote-gate-bench.json)。

## Kitchen PR #227：D64 小查询块

修改 `sage_attn_launcher.cu`，仅对 SM120、无 mask/无 prepared mask、32 query/key heads、D64、batch≤8、相等的 Q/K 长度 1024–2048、正 scale 使用 CTA_Q=64/WARP_Q=16。原 CTA_Q=128/WARP_Q=32。保持 K tile=64、128 行量化 scale 分组、softmax 与 PV 累加语义；不启用 cached-Q，不更改公共 API。

独立 kernel A/B：16 组 dtype/shape、所有候选输出 exact；18 组 public prequantized API 测试含 2049 fallback。代表 `[4,32,1797,64]`：FP16 0.238291→0.227432 ms（−4.56%）；BF16 0.242810→0.228682 ms（−5.82%）。batch1 约 −6.8%/−7.0%，batch8 约 −1.4%/−1.9%。

新增 10 组 split-head oracle：32heads 触发新 tile，分为两个 16heads 调用旧 tile；heads 独立且量化组相同，逐字节比较，覆盖 interleaved QKV、FP16/BF16 与尾块。

完整 suite：current-main Python API + 新 launcher 为 429 passed / 594 skipped / 2 failed；**未修改的 main launcher 复现相同两个 zero/negative scale 失败**，由 #224 处理。保留 #224 等既有改动的组合候选为 527 passed / 594 skipped / 0 failed。

最初仅替换 attention 入口的整段 decode：243 帧 9.929252→9.874037 s（−0.556%），260 帧 10.627293→10.590084 s（−0.350%），12 次含预热的浮点 RGB 与 RGB8 SHA 全部相等。整库多模块切换时，未改动的 GEMM 入口出现额外变慢，attention 本身仍更快。随后改为每个独立进程只加载一个扩展的 ABBA 复验：每进程一次预热、两次正式，原版 **9.962410 s → 候选 9.866619 s（−0.9615%）**，12 次解码的浮点 RGB/RGB8 哈希全部一致。因此不能用多模块切换的结果表示单库部署；底层绑定/状态相互影响的精确机制没有进一步证实。独立进程数据见 [记录](../evidence/pdmd-kitchen-1001/d64-isolated-decode.json)。

新增公共 prequantized API 独立进程脚本已在卡上跑完 12 组形状/dtype、四进程 ABBA。代表尺寸 FP16 −4.55%、BF16 −4.80%，最小1024长度/单batch基本中性，2049 fallback变化小于0.09%。这组数据包含API调度，和最初直接kernel计时分别列出；并非整个请求加速。
