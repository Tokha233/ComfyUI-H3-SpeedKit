# 性能账本与累计收益口径

新同场实测：**Kitchen 0.2.35 基础 Larry v4 8 步＋原生 FP16 视频 VAE → 固定 R85＋INT8 视频 VAE，两个代表片段的总生成耗时减少 11.591%，串行容量折算增加 13.111%**。每请求平均节省 30.66 秒。完整计时从冻结 condition 到本地 MP4，排除 Qwen/参考处理、HTTP/排队/上传与首次读权重。

主对照与阶段范围见 [原生FP16基线实测](R85-NATIVE-FP16-VS-R85.md)。以下保留各自历史分母，第9节是两边均为INT8 VAE的辅助对照。

## 1. 三种“原版”不能混称

| 名称 | 模型/采样 | 算子与 VAE | 能回答的问题 |
|---|---|---|---|
| 早期部署 v22 | baked 旧 Turbo4，5 次实际 NFE | Kitchen .33 原路径＋TRT VAE；已有 DynamicVRAM/异步 export | 当时累计工程优化的完整服务收益 |
| Kitchen .35 stock 回放 | Larry8 的一个真实第一步输入 | 新 Kitchen 基础 kernel，关闭项目迁移融合 | 迁入原融合能保住多少 forward 收益 |
| R85 之前的累计实验基线 | Larry v4 / Euler beta8 | 已含历史融合、INT8 VAE、gate epilogue 等 | R85 的新增 1.9% |

R85 不是裸 Kitchen；9/24 r3/r5 服务镜像也不是 v22。BF16/50 A800 仅是质量参考，不是以上任一速度分母。

## 2. 计时分类与计算公式

| 层级 | 起止 | 不应冒称 |
|---|---|---|
| kernel / 算子链 | CUDA event 的目标算子范围 | 完整请求耗时 |
| DiT forward 回放 | 一个完整 50-block forward | 8-step 推理或服务吞吐 |
| 视频 VAE | 按该实验记录的 load/decode/output/unload | DiT＋condition 的整体收益 |
| 固定 condition 完整生成 | 冻结条件到双 VAE＋本地 MP4 | 真实 condition、HTTP 排队与上传时延 |
| 完整 GPU pipeline | 真实 condition＋DiT＋双 VAE | 已包含 CPU 编码的端到端 |
| worker 完成周期 | 出队到最终成片/结果成功 | 含外部排队的用户 SLA |
| backlog 吞吐 | 实际连续成片完成间隔 | 单请求秒数倒数或集群 P95 |

`耗时减少 = (TA − TB) / TA`；`相同工作量串行容量增加 = TA / TB − 1`。例如耗时少 40% 对应阶段容量增加约 66.7%，不意味着整机容量增加 66.7%。

存在 CPU/GPU 重叠时，吞吐应直接按完成事件计算。多卡实验先做各卡 A/B，再按相同工作量 GPU 秒汇总；不能用最快卡 B 减最慢卡 A，也不能把 GPU 秒之和当多卡墙钟时间。

### R85 原始配对计算

7 个工作组覆盖 `[1]、[8]、[2,3,4]、[5,6,7]、[9,10,11]、[12,13]、[14,15]`。每组 ABBA/BAAB，先独立预热；各组同卡取 A/B 均值，再求和。不能直接平均每个 case 的百分比。

资料包附每组正式秒数、请求四 SHA 和源 JSON 的 SHA。执行 `python3 tools/verify_metrics.py` 会重新得到 3295.244819 / 3232.463433，而不是只检查报告已经算好的百分比。

## 6. 新 VAE 候选的收益和限制

| 候选 | 对照 | 测试范围 | 结果 |
|---|---|---|---|
| 仅静态 VAE | R85 动态 VAE | case1/8 完整生成，各 2 正式/臂 | 239.806487→239.333983；227.580350→227.129878 s，约 0.20% |
| 静态＋R207 RoPE | R85 动态 VAE | 全 15 保存 latent | 视频 −6.801731%；双 VAE 147.427484→138.144219 s，−6.296834% |
| 静态＋R234v2/R244 | 静态＋R207 | 全 15，30 预热＋60 正式 decode | 视频 136.018638→135.159510 s，−0.631625%；双 VAE −0.774287% |

## 7. GPU 利用率怎样解释

### R85 DiT：活动覆盖接近连续，主要时间在 dense

一次完整 profile 的 DiT GPU window 为 225.815693 s；kernel union 225.147438 s，约 99.70%。dense 170.891387 s，占 75.68%；其他 GEMM 34.253688 s，融合 QKV 15.103506 s。未被 kernel 隐藏的 copy 0.045101 s；无记录活动间隙 0.621164 s，约 0.275%。

这说明靠消除 CPU 空隙最多只能回收很小部分，并不代表 Tensor Core 达到 99.7% 理论峰值。dense 与同卡 pure-MMA 微基准之比约 95.3% 也只是参考实验比值，不是全 DiT 的厂商理论利用率。来源 S15、S27。

### VAE：GEMM 是主要成本，5 秒未达到

R234/R244 的 case1 profile：kernel span 8.347711 s，kernel union 8.217999 s（98.45%）；其中 INT8 GEMM 5.341502 s（约 65%）、attention 0.834016 s、量化/ConvRot/RoPE 1.802490 s。

全 15 按 `170 SM × 2048 dense INT8 ops/SM/cycle × 实测时钟积分` 作普通 GB202 架构参照，工作量加权效率约 49.27%→50.87%。这不是 NVIDIA 保证的 D v2 SKU 峰值，混合精度、softmax、量化、同步、加载和输出均不可能免费。

FC1/FC2 NCU Tensor 管线约 83%/88%；与 pure-MMA 实验比值约 95.57%/91.97%。这些与整 VAE 的 50.87% 分母不同。不能说“还闲置一半算力，所以应能再快一倍”。仅 GEMM 已约 5.34 s，即使 attention 免费，当前仍无法实现完整 VAE<5 s。来源 S20–S23。

## 9. 新增直接同场比较：stock Kitchen 0.2.35 → R85

9/29 新 GPU 同场实测：相同 Larry v4 8 步、同一 INT8 VAE，Kitchen 0.2.35 基础实现到固定 R85，两个代表性片段的总生成耗时减少 **6.685%**，串行容量折算 **+7.164%**。共 8 正式＋8 预热，所有正式请求的 video latent、audio latent、RGB8、PCM 与历史黄金逐位一致。

相同工作量合计 500.735980→467.259363 GPU 秒，总耗时减少 6.685%；DiT 减少 6.477%；每请求平均节省 16.738 秒。先对每个 case 的同卡正式记录取均值，再合并等量工作量，不能把 GPU 秒之和写成多卡墙钟。

| Case | 基础至 MP4 / s | R85 至 MP4 / s | 总耗时减少 |
|---|---:|---:|---:|
| 1 | 257.364477 | 239.823806 | 6.815% |
| 8 | 243.371504 | 227.435557 | 6.548% |

这场对照使用独立进程，stock 不导入任何项目 DiT 补丁。两臂共享已经预合并的权重、INT8 VAE、DynamicVRAM 与 CPU 编码器；stock 走原生 FP32 CPU 视频输出，R85 启用 RGB8/pinned D2H。完整计时包含本地 MP4，排除 Qwen/参考处理、HTTP/上传及首次读权重。

每片段每臂仅 2 次正式，此结果不等于全 15 片段或线上 P95；没有测连续队列的异步吞吐。历史 TRT→INT8 的约 40% 解码降时没有包含在此分母中，后续静态 VAE/R234/R244 也没有纳入。当前可以用这个直接实测替代“总收益未知”，同时保留这些范围限制。

详见 [逐阶段时间和复算证据](R85-STOCK-VS-R85.md)；公开复算命令：`python3 tools/verify_stock_comparison.py`。
